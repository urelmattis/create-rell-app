# Triage Labels

The skills speak in terms of five canonical triage roles. This file maps those roles to the actual label strings used in this repo's issue tracker.

| Label in mattpocock/skills | Label in our tracker | Meaning                                                                            |
| -------------------------- | -------------------- | ---------------------------------------------------------------------------------- |
| `needs-triage`             | `needs-triage`       | Maintainer needs to evaluate this issue                                            |
| `needs-info`               | `needs-info`         | Waiting on reporter for more information                                           |
| `ready-for-agent`          | `agent-explore`      | Fully specified; hand it to the agent queue (exploration first, see below)         |
| `ready-for-human`          | `needs-human`        | Requires a human — a judgment call, a credential, a design decision, a manual test |
| `wontfix`                  | `wontfix`            | Will not be actioned                                                               |

When a skill mentions a role (e.g. "apply the AFK-ready triage label"), use the corresponding label string from this table.

## The agent queue behind `ready-for-agent`

Handing an issue to an agent is two steps here, each run by a sandboxed GitHub Actions workflow (`.github/workflows/agent-*.yml`). Every new issue is explored on its own; a `trivial` or `ready` verdict goes straight to implement, and a person is only in the loop for `needs-human`, `already-fixed`, and the merge:

| Label                | Who applies it                               | What happens                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `agent-explore`      | the workflow, on every new issue; or a human | An agent reads the issue and the codebase, changes nothing, posts a verdict comment (`trivial` / `ready` / `needs-human` / `already-fixed`), then swaps this label for `explored`. A run that ends without a verdict fails and adds `needs-human`                                                                                                                                                                                                                                       |
| `explored`           | the agent                                    | The verdict is on the issue. `trivial` and `ready` dispatch implement at once; the other two wait for a person                                                                                                                                                                                                                                                                                                                                                                          |
| `already-fixed`      | the agent                                    | The code already does what the issue asks; the comment names the lines. A person closes it                                                                                                                                                                                                                                                                                                                                                                                              |
| `agent-implement`    | the explore workflow; or a human             | An agent implements on `agent/issue-<number>`, runs typecheck/lint/test, opens a PR labeled `agent-pr`, removes this label. A run that ends with no PR and no `needs-human` note fails and adds `needs-human`                                                                                                                                                                                                                                                                           |
| `agent-pr`           | the agent                                    | A PR opened by an agent; the review workflow posts a two-axis review on open, never approves or merges                                                                                                                                                                                                                                                                                                                                                                                  |
| `review-ready`       | the review workflow                          | The reviewer's last verdict was "ready to merge"; cleared by any other verdict or by a new commit. On an `agent-pr` PR under 400 changed lines that stays off the protected paths, it also enables auto-merge                                                                                                                                                                                                                                                                           |
| `re-review`          | human                                        | Ask the review workflow for another pass; it clears the label when done                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `review-addressed`   | the address workflow                         | The first address-the-review round was started on this PR (`agent-address.yml`); the agent takes the review's defects and in-scope items, declines the rest with reasons in a `## Review response`, and pushes what it took. A second "needs changes" gets a second round                                                                                                                                                                                                               |
| `review-addressed-2` | the address workflow                         | The second round was started; it reads the first round's response and does properly what the reviewer says is still wrong. The next "needs changes" is a person's                                                                                                                                                                                                                                                                                                                       |
| `conflict-round`     | the address workflow                         | One merge-main round was started on this PR (`agent-address.yml` with brief `merge-main`); the agent merges `main` into the branch, resolves the conflicts keeping both sides' intent, pushes the merge commit if it can (otherwise it aborts the merge and says why), and posts a `## Merge response`. The next conflict with `main` is a person's                                                                                                                                     |
| `needs-human`        | triage / agent / an assert step              | Blocked on something only a person can do. On a PR: the queue stopped after a review it cannot act on ("needs a human decision", a third "needs changes" after two rounds, an unreadable verdict, a non-agent branch or a fork, a round that took nothing, a round that ended without its response, a merge-main round that pushed nothing or still conflicts after its push, or a second conflict with `main` after that round); answer on the PR, push if needed, and add `re-review` |
| `security`           | scheduled review                             | A finding from the Monday security sweep; explored automatically                                                                                                                                                                                                                                                                                                                                                                                                                        |

`epic` and `story` describe what an issue _is_; the labels above describe where it is in the queue.

## What runs with nobody watching

- A new issue is explored within minutes; `trivial` and `ready` verdicts are implemented and reviewed without a person in between.
- The Monday sweep files `security` issues and explores them.
- Branches are not required to be up to date with `main` before merging, so nothing has to rebase or re-run when `main` moves; a PR's checks run once, on its own head.
- Dependabot minor and patch updates merge on their own once CI passes (`dependabot-auto-merge.yml`); majors wait.
- An agent PR whose review says "ready to merge" merges on its own once the required checks pass, provided the diff is under 400 changed lines and touches none of the protected paths: `.github/`, `.claude/`, `CLAUDE.md`, `CONTEXT.md`, `docs/agents/`, migrations, any `package.json`, the lockfile, `supabase/`, auth middleware, build and infra config, and the files that define the gates (`.husky/`, ignore files, lint, TypeScript and test configs). Those, larger diffs, and anything a review did not call ready stay with a person.
- A new commit on a reviewed PR clears `review-ready` and switches auto-merge off; `re-review` asks for another pass.
- An agent PR whose review says "needs changes" gets up to two address-the-review rounds: a fresh session on the PR's branch takes the items that are defects or in scope, declines the rest with a reason, pushes one commit (which runs CI), and a fresh review is dispatched. If that review says ready, tier 3 merges as usual; if it says needs changes again, a second round runs with the first response in front of it; a third "needs changes" puts `needs-human` on the PR and a person decides between the review and the responses. A round that takes nothing also stops with `needs-human`. The cap is two rounds per PR, so a disagreement ends with a person, never a loop.
- An agent PR the review passed that conflicts with `main` gets one merge-main round: the same workflow with a different brief merges `main` in, resolves the conflicts keeping both sides' intent, pushes the merge commit, and a fresh review follows; the merge job catches a conflict it can see, and the daily housekeeping catches one that appears later under an enabled auto-merge. A second conflict, or a resolution the round cannot make without a design decision, stops with `needs-human`.
- A review run built from a stale merge ref in the minutes after `agent-review.yml` changes on `main` (the action refuses a workflow file that differs from `main`'s) dispatches itself again by name instead of failing.
- A merge performed by auto-merge is done by the workflow token, and GitHub then neither closes the linked issue nor deletes the branch; the daily `queue-housekeeping.yml` does both, so an issue can stay open for up to a day after its fix lands. Three exceptions: an issue a person reopened after the merge stays open; an issue whose timeline could not be read stays open until a later run can read it; a branch that has moved on since the merged PR (a re-dispatched issue reusing the name) is left alone.
