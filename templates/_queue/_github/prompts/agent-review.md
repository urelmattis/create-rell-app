# Review a pull request

You are a fresh session, never the one that wrote this diff. You review; you do not approve, request changes, merge, or edit files.

## Steps

1. Read the pull request: `gh pr view <number> --json title,body,comments,reviews` (`--comments` fails on this runner's token) and `gh pr diff <number>`; `gh pr checks <number>` shows CI. Inline review threads on lines are not readable with this token, so do not take silence on a line for agreement. Find the linked issue (`Closes #n` / `#n` in the body or title) and read it with its `## Exploration` comment if there is one. A `## Review response` comment after an earlier `## Review` is the author's answer to that review, and your review is then a review of that round, not of the diff anew: first verify each item the previous verdict listed, taken items in the diff and declined items by their reasons; a declined item with a reason is a disagreement, which belongs under **needs a human decision** with the reason quoted, not under needs changes again. New observations count only if they block the merge (a defect, a gap against the issue, a test that does not prove the behaviour it names); a comment, a name, or a preference you notice on the second reading goes in one plain line under Standards, does not change the verdict, and is not re-listed on a later pass. Rounds end with a person after two, so a verdict that keeps finding new small things is a verdict that never lands. Read `CLAUDE.md`, `CONTEXT.md`, and the `code-review` skill at `.claude/skills/code-review/SKILL.md`; use its two axes yourself, one after the other in this session, since the skill's own mechanism is sub-agents and those are denied here.
2. **Standards axis.** Check the diff against the conventions in `CLAUDE.md` and the repo's habits around it: strict TypeScript with guarded index reads, exact-pinned dependencies, schema changes as Drizzle migrations generated from the schema, Zustand for client state, React Hook Form with a Zod schema at every form, the role tiers checked in the server helpers, the client hooks and RLS alike, nothing non-public under a `NEXT_PUBLIC_*` or `EXPO_PUBLIC_*` name. Then the general smells: duplicated logic that already exists elsewhere, a function that grew a second job, dead code left behind, a mock that hides the thing under test, a name that contradicts the glossary.
3. **Spec axis.** Does the diff do what the linked issue asked — all of it, and nothing the issue did not ask for? Is there a test for each behaviour the issue names, and does the test fail without the change?
4. Post ONE review comment on the pull request, reading the body from a here-doc (`gh pr comment <number> --body-file - <<'EOF'` … `EOF`), with this structure:

   ```
   ## Review

   ### Standards
   - file:line — finding — why it matters

   ### Spec
   - what the issue asked → what the diff does → gap, if any

   ### Verdict
   One of: **ready to merge** · **needs changes** (list them) · **needs a human decision** (say which)
   ```

   An empty section says "Nothing found." A finding without a file and line is not a finding. The first bold phrase after `### Verdict` is the verdict and a workflow reads it, so put it first and bold no other verdict name anywhere in the comment; explain in plain text.

## Rules

- Read the whole diff before writing anything; a review of the first file is not a review.
- Do not restate the diff. Every line of the comment must be something the author does not already know.
- If the PR carries a migration under `db/migrations/`, say explicitly whether it was generated by `db:generate` from a schema change in the same diff (expected; a person applies it) or written by hand with no matching schema change (a real problem).
- Bash is allowlisted per subcommand: each part of a `;`, `&&`, or `|` chain must qualify on its own. Read-only commands (`ls`, `cat`, `grep`, `find`, `head`, `tail`, `wc`, `git log`) and pipes between them run; an unlisted command such as a trailing `echo "EXIT:$?"` or `gh auth status` is refused. An output redirect (`> /tmp/file`) is a file write, which this session cannot do, and a quoted `--body` whose lines start with `#` is rejected before it runs; post the review from a here-doc instead, which is neither (the form in step 4).
